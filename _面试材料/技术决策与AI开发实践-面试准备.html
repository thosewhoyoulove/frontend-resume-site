AI 辅助开发：面试口述准备 ​

面试官问“你怎么用 AI 写代码”时，重点不是工具数量，而是你如何把 AI 放进可控的工程流程：先明确问题和边界，再让 AI 协助分析和实现，最后由自己通过代码、测试和运行结果验收。

text
明确需求与约束
  → 让 AI 理解上下文并比较方案
  → 拆成可检查的改动
  → 分步实现
  → 代码审查、测试、构建和页面验证
  → 把稳定经验沉淀为文档或规则

回答时要说明：工具解决了哪一类问题，你做了什么判断，最后如何证明结果可用。

一、主干口述（约 1.5–2 分钟） ​

我平时使用 AI 工具比较多，主要是 ChatGPT、Cursor 和 Codex。但我不会简单地把它们当成代码生成工具，而是根据开发阶段和任务复杂度来选择。

首先是 ChatGPT。我主要用它做技术方案讨论、复杂问题分析和知识补充。

比如在我们 Agent 前端项目中，涉及 SSE 流式解析、跨产品 iframe 通信，以及共享模块的架构设计。我会先和 AI 讨论不同方案的优缺点，包括边界条件、潜在风险和异常场景，再结合实际业务和代码做判断。

其次是 Cursor。这是我日常编码过程中使用比较频繁的工具。

对于已有代码库，我会利用它理解上下文、分析组件依赖、辅助实现功能和重构代码。尤其在修改多个相关文件时，我会先让它分析影响范围，再拆分任务执行，而不是直接让它生成一大段代码。

另外是 Codex。我主要关注它在相对独立、目标明确的工程任务中的应用，比如代码重构、补充测试、排查 Bug，以及执行一些可以通过测试或构建验证的任务。

我认为 AI 辅助开发最重要的不是生成代码的速度，而是如何控制生成结果的质量。

所以我的使用习惯是：先明确需求和约束，再让 AI 制定方案，确认后分步实现，最后通过代码审查、类型检查、测试和实际运行来验证。

对于项目中比较稳定的架构规范、编码约束和常见问题，我也倾向于把它们沉淀成项目文档或 AI Rules，让 AI 在后续任务中能够遵循统一的工程约定。

我觉得 AI 真正带来的价值，是让我把更多精力投入到架构设计、复杂业务分析和代码质量控制上，而不是单纯减少写代码的时间。

口述骨架 ​

  1. 工具：ChatGPT / Cursor / Codex，按阶段选择
  2. ChatGPT：方案讨论、边界与风险
  3. Cursor：读上下文、改多文件、先拆再写
  4. Codex：独立任务、重构、测试、可验证排查
  5. 原则：控制质量，不是追速度
  6. 流程：需求约束 → 方案确认 → 分步实现 → 审查验证
  7. 沉淀：文档 / Rules
  8. 价值：把精力放到架构、业务和质量控制

二、按工具展开：面试官继续追问时怎么答 ​

1、ChatGPT：先讨论方案，再动手改代码 ​

适合问题还不清楚、需要比较方案的时候。

常见用法：

  • 梳理一个复杂交互的状态流转
  • 比较几种实现方式的边界和风险
  • 补齐自己不熟的协议、浏览器行为或架构背景

项目例子可以讲 Agent 前端：

  • SSE 流式解析：网络分块、事件归并、终态收敛
  • 异步竞态：AbortController 与执行序号分别解决什么问题
  • 公共模块：哪些能力适合下沉到 agent-core，哪些业务应留在产品侧

回答时要强调：AI 给出的是候选方案，不是最终结论。最终仍由自己结合业务和现有代码判断。

2、Cursor：在真实代码库里协作 ​

适合已经进入实现阶段的日常开发。

常见用法：

  • 顺着页面操作路径理解陌生模块
  • 分析组件依赖和改动影响面
  • 辅助实现功能、局部重构、补齐边界处理

项目例子可以讲高级筛选：

DimensionSelector 需要先拿到维度配置，才能转换筛选条件。条件先到、配置后到时，立即转换就存在时序问题。

现有代码在配置缺失时，将条件暂存在 pendingValue。配置到达后，优先取出这个值，清除暂存内容，再执行转换，避免空的 defaultValue 覆盖待回填条件。

这个例子适合说明 Cursor 的正确用法：先追踪 setValue 调用，再检查配置到达后的处理，最后核对默认值与待回填值的优先级。不要一上来让它整页重写。

源码记录：挂起回填、配置到达后恢复。

3、Codex：承接目标明确、可验证的任务 ​

适合边界比较清楚、结果可以用命令或测试验收的工作。

常见用法：

  • 局部重构
  • 补充测试
  • 排查已有复现路径的 Bug
  • 跑构建、lint、测试并汇报结果

这类任务的关键是验收条件要先写清楚。比如“补一组 SSE 跨块解析测试”，比“优化一下流式代码”更容易检查。

三、质量控制和工程沉淀 ​

1、我实际怎么控制 AI 输出质量 ​

我通常按四步走：

  1. 先明确需求和约束。 改什么、不改什么、验收标准是什么。
  2. 再让 AI 给出方案。 看它有没有理解调用链、状态边界和已有约定。
  3. 确认后再分步实现。 一次改一个风险点，而不是让它整页生成。
  4. 最后做验证。 代码审查、类型检查、测试、构建，以及必要的页面验证。

如果一次改动同时碰到条件回填、模式切换、视图切换和任务恢复，就先拆开。原因是这些模块状态互相影响，整包交给 AI 很容易漏掉边界。

高级筛选里可以这样拆：

  1. 先确认生成结果的契约：什么状态才算可应用
  2. 再处理条件回填
  3. 再检查普通筛选 / 智能搭建、表格 / 卡片的状态隔离
  4. 最后验证任务恢复和旧回调隔离

相关机制可参考：

  • 生成结果进入既有筛选系统：结果校验与应用、统一条件回填
  • 模式与视图状态隔离：工作区缓存读取、双视图 state
  • 流连接与任务恢复：requestId / AbortController 管前端连接，taskId 管服务端任务续接；页面返回后 5 分钟内可续接，不等于任意断网自动重连。源码见 SSE 解析、重新进入恢复、缓存有效期

2、为什么要沉淀文档和 Rules ​

稳定的约定不适合每次重新口述给 AI。

更合适的做法是：

  • 用文档记录架构决策和状态流转
  • 用 Rules / AGENTS.md 固定请求层、目录结构、样式和提交前检查
  • 把高频检查流程整理成 Skills，方便重复执行

规则要具体。比如“修改流式任务时，检查连接取消、请求序号失效和回调写入条件”，比“注意异步问题”更容易执行。

当前环境中已有可参考材料：

  • D:/tungee-agent/AGENTS.md：统一请求层、CSS Modules、路由、lint / build
  • D:/tungee-agent/docs/agent-rules/：页面、组件和全局规范
  • 本地 sales-merge Skill：提交范围检查、分支集成、验证和结果汇报

面试时要分清：这些材料说明环境里已经有工程化基础；个人贡献还要补充自己编写或维护了哪些部分，谁使用过，解决过什么重复问题。

3、我对 AI 价值的判断 ​

AI 真正省下的，不只是敲代码的时间。

更重要的是，它把一部分检索、草稿实现和机械排查承接掉了，让我能把时间用在：

  • 架构边界是否合理
  • 复杂业务状态有没有漏
  • 改动有没有可验证的质量门槛

所以我更愿意把 AI 当成协作流程的一部分，而不是单纯的代码生成器。

四、简历对应与补齐项 ​

当前简历中的表述是：能够使用 Cursor、Codex 等 AI Coding 工具辅助需求拆解、代码实现、重构与问题排查，注重代码审查、类型约束及测试验证。

面试口述可以按本文补上 ChatGPT，并讲清三者分工。如果简历要同步，再单独改简历文案。

正式面试前，最好再补齐一个亲自完成的案例：

  1. 当时接到什么任务
  2. 自己负责哪一段
  3. AI 分别做了什么
  4. 哪项判断由自己作出
  5. 最终用了什么方法验证

高级筛选项目还要明确个人负责范围和智能搭建的实际参与时间。简历中的“2025.05—至今”是整个高级筛选项目时间，不能直接作为智能搭建的开发起始时间。前端参与范围应围绕生成能力接入、交互和状态管理说明；模型训练与条件生成算法需要独立证据。

五、可参考的公开实践 ​

  1. OpenAI：Using skills to accelerate OSS maintenance

    用 AGENTS.md 记录仓库约定，把校验、文档同步和发布检查整理成 Skills。

  2. Anthropic：Claude Code power user tips

    介绍维护说明文件、封装高频操作，以及把一次纠错沉淀成后续检查项。

  3. 美团：用 Agent 评测思路管理 AI Coding

    以 Rule 固定约束，以 Skill 组织任务，再从典型迁移沉淀标准流程。

  4. 腾讯 CodeBuddy：Rules

    介绍项目规则的版本管理、文档引用和按条件加载。适合参考规则组织方式。
