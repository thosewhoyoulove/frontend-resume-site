项目亮点：深度面试训练 ​

配合 技术尽调与源码证据 使用。编号 F1—F4、S1—S3、A1—A4 与该报告对应。

下面的 STAR 是基于现有实现的口述参考，不是个人贡献证明。只有你确实做过的动作才能改成“我设计/我实现”；原始故障、比较过程、上线效果没有证据时，应说“当前实现采用”“现在复盘我会选择”。实验除标明本轮已执行的部分外，都还需要动手完成。

每条亮点的 15—20 分钟训练节奏：2 分钟说明约束和个人职责，4 分钟画数据流并读关键代码，4 分钟解释替代方案和代价，4 分钟推演异常时序，3 分钟讲验证方法与结果。面试现场先用 60—90 秒回答，再随追问展开，不一次背完。

F1：模式隔离、快照与延迟回填 ​

一级问题： AI 条件与普通筛选共用页面，如何避免互相覆盖？

二级追问： 为什么只把条件放进 Redux 不够？setState 的回调已经执行，为什么还传查询快照？

三级追问： AI 结果先到、配置后到、用户中途改条件时谁优先？relation=0、空条件、主体变化、组件卸载如何处理？

STAR 参考： S：存量页面同时承载普通条件、智能条件和两类结果视图，筛选器还依赖异步配置。T：让本次应用的条件、编辑器显示和提交查询保持一致。A：当前实现按模式分仓，用统一快照入口回填；配置未到时挂起 pendingValue，配置到达后再转换；查询显式携带本次条件。R：代码形成了可追踪的回填路径，可验证配置晚到和关系值回填；没有线上统计时不说故障下降比例。个人负责哪一段，应补充具体改动。

关键代码与原理：

js
// 源码逻辑节选：并非本轮新实现。
if (!configs) {
  this.pendingValue = value;
  return;
}
// applyFilterSnapshot 的 setState callback 内：
instance.handleFilterSnapshotSearch(filterData, filterRelation, options);

setState 回调只说明对应组件的更新完成，不意味着另一个组件依赖的配置已就绪，更不意味着稍后读取的可变状态仍等于本次查询意图。快照减少对“此刻最新 state”的隐式依赖，但仍要看对象是否会被后续修改，不能自动声称深度不可变。

方案对比与质疑： 单个全局 Store 可以承载状态，但仍需分清草稿、已提交条件、服务端结果与任务状态；把所有字段搬进 Redux 不会自动消除竞态。当前命令式回填适合存量渐进改造；重写成全受控组件更统一，却牵涉调用方和旧生命周期，成本更大。用户编辑与异步生成的优先级应明确成版本/dirty 规则，当前不能假设完整覆盖。

动手实验： 用 deferred promise 控制配置和生成结果的到达顺序；枚举结果先到、配置先到、两次回填、期间清空、relation=0/1、切主体。断言展示值和请求体属于同一次提交；增加“旧主体 pendingValue 不得落入新主体”的用例。

F2：结果复用与忙碌期间的最新查询 ​

一级问题： 你做的缓存具体缓存什么？什么时候命中、什么时候失效？

二级追问： 双视图分开 state 为什么仍需 queryKey？loading 时再次查询是丢弃、排队还是取消旧请求？

三级追问： A→B→A 时 A 的旧响应能否提交？相同条件在不同用户权限下能共享吗？一个调用者 abort 是否应取消共享请求？

STAR 参考： S：卡片和表格接口及分页不同，用户频繁切换，并可能在请求未结束时再次筛选。T：复用可用结果，同时保留最新查询意图。A：当前两种视图保存独立结果和查询键；切换时只为未命中的视图取数；忙碌期间用单槽保存最新快照，请求结束后续查。R：参数键匹配且已完成查询时可跳过重新取数；这是一种页面内结果复用，尚不是具有 TTL 和 in-flight 去重的完整请求层。

关键代码与原理：

js
// 现有判定；fresh 指参数匹配，不代表服务端数据仍然新鲜。
this.state.cardHasSearched &&
  this.state.cardSearchKey === this.getCardSearchKey();
// 忙碌结束再执行最新待查条件，而非执行每一次中间点击。
if (prevSearching && !searching && this.pendingFilterSearch) {
  this.handleFilter(undefined, scroll, searchContext);
}

queryKey 表达查询语义，generation 表达一次请求归属；即使 A→B→A 的键相同，旧 A 与新 A 也可能对应不同时间的数据，所以二者不能互相替代。

方案对比与质疑： 串行续查实现简单，但最新结果必须等待慢请求；取消旧请求 + generation 更及时，但所有提交和清理分支都要验证；TanStack Query/RTK Query 等工具的引入也需要先定义 key、权限隔离、失效及副作用边界，不能靠引包完成设计。当前查询键没有 TTL 语义，不能承诺数据实时。

动手实验： 卡片→表格→卡片，记录固定条件下请求数；改变排序、页码、条件后必须重新取数。用可控 promise 注入 A 慢成功、B 快成功、A 迟到错误；断言旧 success/error/finally 均不能覆盖当前结果或关闭当前 loading。随后实现按 key 共享 promise 的小实验，证明单个订阅者退出不会误取消其他订阅者。

F3：任务恢复与请求失效 ​

一级问题： 你的任务恢复是不是断点续传？

二级追问： taskId、requestId、eventId 各自解决什么问题？为什么同时用 AbortController 和请求序号？

三级追问： 后端已经完成、前端还在播放动画时被外部结果替换，abort 有用吗？过期时间从何时计算？任务恢复时权限发生变化怎么办？

STAR 参考： S：生成过程较长，用户可能离页，后端任务与前端连接生命周期不同。T：返回页面时复用仍有效的任务，并避免旧连接回写新界面。A：保存用户/主体下的 taskId、输入、开始时间和阶段快照；有效期内携 taskId 续接，已完成阶段跳过动画；用序号失效旧回调并 abort 连接，嵌入场景关闭恢复。R：具备任务级恢复路径；没有消息游标重放证据时，明确不称断点续传。

关键代码与原理： 源码 shouldCancel 比较捕获的 requestId 与 ref；退出时先加序号再 abort。taskId 是后端任务身份，requestId 是前端某次连接/执行身份。即使是恢复同一个 taskId，也应生成新的 requestId。五分钟从 startedAt 计算，不是最后保存时间。

边界与质疑： 外部回填分支目前没有同步加序号，若旧 promise 已完成，abort 不能撤销等待展示队列的后续 then。候选人应能解释这个反例，而非回答“双保险绝对不会错”。让所有 reset/replace/stop 都调用统一 invalidate 是拟议改进。后端取消要明确 API，客户端断开不能代替。

动手实验： 用 fake timers 推进开始后 4:59 与 5:01；验证普通页/嵌入页、缺 taskId、失败终态、404/410。用可手动 resolve 的展示 promise 重现“旧流完成→外部回填→放行旧 then”，先确认旧结果覆盖是否可达，再用统一 invalidate 修复并保留回归用例。

F4：AI 输出进入确定性业务系统 ​

一级问题： 为什么不能看到生成总结就发起筛选？

二级追问： HTTP 200、流结束、ready、条件合法分别代表什么？为什么选择 POST Fetch SSE？

三级追问： JSON 合法但操作符不支持怎么办？ready 后又收到错误怎么办？手工修改、保存、分享如何保持同一条件语义？

STAR 参考： S：生成能力提供流式阶段和最终条件，页面需要继续支持编辑、查询和保存分享。T：让生成结果成为既有业务系统可处理的输入。A：网络层区分阶段、错误和结果；业务层要求 ready 以及条件对象，再进入统一回填入口；使用既有筛选器和保存分享能力。R：形成生成到业务操作的闭环；“对象存在”只保证基础形状，不夸大为完整条件验证。

关键代码与原理： getAdvancedFilterAgentBuildFilter 检查对象且非数组，容器检查 ready。POST 允许提交输入，Fetch 可接入现有请求与取消能力；代价是要自行处理读流、协议解析与恢复。原生 EventSource 的接口不提供自定义 POST body；选择要依据请求协议，而非笼统说 Fetch 更高级。EventSource 规范。

方案对比与边界： 若只有单向流，SSE 简洁；WebSocket 适合协议确实要求双向长连接的场景，但会引入额外连接与消息协议管理。前端字段 schema 用于尽早反馈，服务端仍必须做权限和条件合法性检查。动画状态、连接状态、任务状态应分别建模。

动手实验： 注入错误 content-type、非2xx、坏 JSON、无终态 EOF、ready 无条件、空对象、非法操作符和重复终态。逐项明确是保留编辑、允许重试、提示错误还是忽略；断言保存/分享的是当前确认条件，而非旧 AI 原始结果。

S1：SDK 分层与同步回环 ​

一级问题： BLL、Model、Bridge 各自负责什么？怎样证明分层有价值？

二级追问： React 状态为什么还需要观察模型？远端状态进来后为什么不再次触发广播？

三级追问： 同一宏任务内多次写同一路径会如何合并？不同数组对象表示同一路径时 Map 能去重吗？同步模拟端口是否引入重入？

STAR 参考： S：SDK 跨业务页提供呼叫能力，既有业务逻辑、UI 和宿主通信需要协作。T：在既有架构下接入与维护能力，控制状态传播路径。A：当前 Model 组合 BLL 与 Bridge，本地观察变更按批次发送；远端 keys 用 noWatcherSet 更新后通知 UI，避免被当成新本地操作再次传播。R：业务动作和通信机制有可追踪边界，多个入口可复用。除非能提供本人重构记录，不说整套分层由自己从零设计。

关键代码与原理： createBridge(data).listen(cb) 提供 vm 与动作接口；changeMap.set(keys, value) 汇总写入，setTimeout 延迟发送；noWatcherSet 用静默写路径回放。Map 对数组键按引用比较，只有路径对象引用相同才能直接按这个键覆盖，因此不能凭 Map 就声称“同一路径必然完全合并”。

方案对比与边界： 纯 React store 更贴近渲染，但跨页面仍需通信层；事件命令与状态快照分离有利于迁移，代价是协议与状态一致性要专门验证。替换自研观察器应先证明旧 API 兼容，避免大规模重写呼叫业务。

动手实验： 两个 mock port 构造 A 修改→中心广播→B 回放，记录总消息数，确保不无限回环；增加同路径不同数组引用、嵌套对象替换和同步回调重入。做一个 mock BLL/Bridge 单测，证明 UI 行为不需要真实 worker 才能测试。

S2：iframe、SharedWorker 与生命周期 ​

一级问题： 为什么中间有 iframe？SharedWorker 如何被多页面共享？

二级追问： 新页面怎么获得已有状态？消息在 iframe 加载前发出怎么办？页面退出后谁清理端口？

三级追问： Tab 被强杀而没有 beforeunload 呢？心跳能保证业务消息送达吗？跨顶级站点嵌入的同源 iframe 一定能共享吗？

STAR 参考： S：不同宿主页需要接入 SDK 的公共呼叫状态。T：让页面接入方式与共享状态所在上下文分开。A：现有实现让隐藏 iframe 承接页面与 worker 的消息，加载前排队，worker 维护端口和状态，新页面获取快照；退出时注销登记。R：建立初始化与同步链路。其可靠性受实际浏览器、宿主和生命周期影响，不能说页面关闭仍然无缝保活。

关键代码与原理： iframe 是宿主与资源域间的桥；SharedWorker 是共享 JS 上下文；MessagePort 是通信端点。它们不是同一概念。核心状态先更新再广播；beforeunload 会清理 tab，并存在挂断逻辑。ping 只表明某条连接有响应，不证明特定 command 已被处理或已持久化。

方案对比与边界： BroadcastChannel 提供同源消息广播，中心状态与选主需要自己实现；Service Worker 生命周期不同，不宜直接当作常驻业务状态容器。SharedWorker 同源与宿主环境限制必须验证，不能仅用 iframe 回避浏览器隔离。SharedWorker 文档。

动手实验： 两个 Tab、一个延迟加载 iframe、一个新开的第三 Tab；验证快照和更新。再测关闭持有呼叫的页面、强杀进程、worker 加载错误和嵌套宿主。记录状态传播 p95、端口数及失败表现；避免把本地模拟端口测试当浏览器兼容验证。

S3：兼容降级与通信安全 ​

一级问题： SharedWorker 不可用时具体降级成什么？

二级追问： 降级后还有跨 Tab 一致性吗？API 存在但构造或加载失败怎么办？TypeScript 能保证消息可信吗？

三级追问： origin 正则为什么可能误放行？合法 origin 的其他 iframe 能否伪造消息？并发 getStorage 如何关联回调，卸载怎么解除 listener？

STAR 参考： S：部分宿主不支持共享 worker，仍需要保留基础呼叫功能。T：复用核心业务处理，明确降低的能力。A：当前缺失 SharedWorker 时加载兼容 Bus，通过页内模拟桥和端口复用 coreLogic；业务 API 保持一致。R：有单页运行路径，跨 Tab 共享不在该降级保证内。安全加固和运行中故障切换是后续改进，不伪装成既有成果。

关键代码与原理： if (!window.SharedWorker) 只检测入口存在；ImitatePort 是当前模块中的回调表，并没有跨页面通道。消息来源必须校验 origin、source 和运行时结构，TS 类型在运行时不负责校验。postMessage 文档。

方案对比与边界： 降为单页与实现另一套跨页协调器是两种产品承诺。建议先暴露能力状态，只有业务确需跨页才设计 leader/lease、消息关联、服务端幂等。当前 origin 正则误匹配已做字符串级验证，但未执行线上攻击或证明实际可利用性。

动手实验： 正常/缺 API/构造异常/iframe 超时四组；每组断言暴露的能力。用假 MessageEvent 测精确来源、错误 source、未知 version、畸形 payload；并发两个 getStorage 逆序返回；重复初始化/销毁100次检查 listener 和 timer 数。不要在生产宿主测试恶意消息。

A1：SSE 的字节、字符、行、事件 ​

一级问题： 为什么不能对每个 chunk 直接 JSON.parse？

二级追问： TextDecoder 的 stream:true 解决什么，字符串 buffer 又解决什么？多行 data、注释、CRLF 如何处理？

三级追问： CR 与 LF 刚好跨块怎么办？没有空行的 EOF 应不应该发事件？id/retry 支持在哪里？超大未终止帧如何限制内存？

STAR 参考： S：模型响应持续流入，网络分块不尊重字符或业务事件边界。T：把传输分块转换为稳定业务事件。A：当前使用增量 UTF-8 解码、帧缓冲和 data 解析，之后交产品适配层解释 payload。R：原有分块测试通过，本轮中文/emoji样本33个切点验证正确；同时发现混合换行和EOF兼容契约需要补齐，不能声称完整标准解析器。

关键代码与原理：

js
// 实际源码：两个不同层次的缓冲。
parser.push(decoder.decode(value, { stream: true }));
// read结束后：
parser.push(decoder.decode());
parser.finish();

decoder 保存不完整字节；parser 保存不完整文本帧。JSON 解析是更后面的一层。读取结束并不自动等于业务成功，终态必须由协议决定。

方案对比与质疑： 自写解析器易适配业务协议，但需要维护规范边界；成熟解析库可降低协议维护成本，仍需核实其EOF、事件字段和错误策略。标准要求空行触发事件，本项目 finish 主动吐尾帧是实际兼容行为，改动前需确认服务端是否依赖。HTML SSE 标准。

动手实验： 运行核查实验；再加入每字节一个 chunk、随机分块、多行 data、BOM、空 data、混合换行、无终止帧、超长帧。实现逐行状态机或引入解析库后，对同一业务轨迹做差异测试。明确数据字节上限与错误策略，而不是无限累计 buffer。

A2：事件归并、幂等和数据结构 ​

一级问题： 为什么不能收到事件就 append？为什么不能只按 event_id 去重？

二级追问： 同一 id 的新内容是覆盖、合并还是追加？数组为什么整体替换？map_subtask 为什么用复合键？

三级追问： done 后收到旧 progress 怎么办？seq 回退、重复 delta、无 id、未知字段如何处理？Map 是不是让更新变成 O(1)？

STAR 参考： S：同一任务会发出多阶段更新，历史和实时记录也可能重复。T：让 UI 展示稳定的业务实体，保留必要字段。A：当前用业务键建立 Map 索引，统一 normalize/upsert；子任务按 map_id+index 归并；对象深合并、数组替换，并保留 input_preview。R：重复业务实体可更新同一条目且有纯函数测试；未实现版本拒收，不承诺乱序幂等。

关键代码与原理：

js
const nextEvents = [...events];
nextEvents[index] = mergeEvent(events[index], event);

Map 定位是平均常数级，复制长度为 n 的数组仍是 O(n)，深合并还依赖字段规模。结构化存储和局部订阅可降低特定成本，但要考虑 React 快照不可变和订阅一致性。快照重复覆盖可能幂等，字符串 delta 重复拼接则不幂等；必须由协议区分。

方案对比与边界： 全量替换简单但可能丢省略字段；深合并保留数据却需定义 null、删除字段和数组语义；event log 便于回放但消耗存储与投影计算。当前实现是物化展示状态，不应包装成完整事件溯源架构。

动手实验： 同ID更新、不同事件ID同一子任务、undefined/null、数组替换、无ID、乱序版本、重复delta。为建议的版本协议验证“相同轨迹重复回放，终态一致且工具副作用不重复”；前端展示去重不能代替后端工具执行幂等。

A3：Abort、执行序号与状态机 ​

一级问题： AbortController 已取消，为什么还要 sequence？

二级追问： start/stop/finish 各自如何影响当前执行？旧 finally 会不会清空新执行？

三级追问： 切会话后旧 error 到达怎么办？done 后普通消息把状态改回 running 是否允许？停止生成与停止接收是否同一个动作？

STAR 参考： S：流式会话可切换、重新开始或卸载，旧请求回调存在交错。T：保证只有有效执行可以更新当前会话。A：begin 取消旧连接并创建新 sequence，回调检查 isCurrent，finish 只清理自己；切会话和卸载调用 stop。R：旧run失效与新run保护有代码和测试；业务任务停止及完整状态迁移还需要独立协议。

关键代码与原理：

js
isCurrent() {
  return activeRun?.sequence === runSequence && !controller.signal.aborted;
}
finish() {
  if (activeRun?.sequence === runSequence) activeRun = null;
}

abort 负责资源，sequence 负责提交资格。闭包捕获 runSequence，后续读 activeRun 判断归属；不用依赖 React render 时刻的 state。

方案对比与质疑： 当前事件到状态的映射易维护，但不验证历史状态与迁移合法性。若升级为 reducer/状态机，可约束 pending→running→waiting/completed/failed；waiting 后经确认继续运行，终态后的迟到进度拒绝。不要为了库而引入状态机库，先列出非法迁移和可重现错误。

动手实验： 执行 first.begin→second.begin→first.onError→first.finish；断言 second 不受影响。再补 run→done→late run、wait→confirm→run、stop→late data、旧session detail迟到，区分流控制测试与整个Hook/页面测试。

A4：多产品共享与渲染性能 ​

一级问题： 你抽出来的是组件库，还是可独立复用的运行时？

二级追问： client、manifest、registry 各自解决什么差异？多个扩展都匹配时怎么办？useMemo 为什么不能自动解决长会话性能？

三级追问： 同页同时挂两个产品Provider会串接口吗？高频更新如何批量提交又不丢delta？虚拟列表如何处理动态高度、滚动定位和工具卡片？

STAR 参考： S：sales与tuoke共享会话、工具和预览能力，但接口与产品交互不同。T：减少公共逻辑分叉并保持产品独立交付。A：当前 core 分离协议/runtime/hooks/UI，产品注入 client、manifest 和扩展注册表；各产品保留构建入口。R：共享逻辑已有统一位置，产品扩展不必全部塞进同一组件；接入成本和性能收益仍需测量。个人范围按实际说“参与哪些接口/组件/重构”。

关键代码与原理： registry 按注册顺序 find 第一个匹配项，因此冲突优先级是实际契约；Provider 注入对象不等于所有依赖都局部化，文件下载仍用模块级 client。ConversationStream 的索引和 sections 依赖 events，数组每次改变会使相关 useMemo 重新计算。

方案对比与边界： 共享包减少协议分叉，但发布兼容与依赖管理成本上升。逐帧提交可以减少 render 次数，但不能把 delta 直接覆盖为最后一条；要先按协议归并再提交，并对终态及时flush。虚拟化只减少挂载节点，不能消除上游全量归并成本。

动手实验： 两个不同client的Provider并存，分别下载同名文件，检测全局client串用；为两个产品执行同一套协议fixture。随后回放固定100/1000/10000条事件，测Profiler actualDuration、commit次数、输入响应和堆内存；比较批处理前后，保持事件最终内容完全一致。React Profiler。
