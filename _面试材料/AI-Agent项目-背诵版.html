探迹销售 AI Agent · 背诵版 ​

用途：回答“介绍一下这个项目”“流式消息是怎么处理的”“你如何解决异步竞态”。建议先背第一部分的 2—3 分钟版本，再按追问展开。

一句话先说清楚 ​

这是一个把 Agent 的持续执行过程转换成可展示、可交互会话状态，并通过共享内核供多个业务产品接入的前端平台。

面试官继续追问时，围绕三个问题展开：

  1. 数据怎么进来： 网络 chunk 需要经过增量解码和 SSE 分帧，才能成为业务事件。
  2. 状态怎么稳定： 同一业务事件的后续更新要归并到原记录，旧执行不能写入当前会话。
  3. 能力怎么复用： 流处理、会话和通用 UI 下沉到公共模块，接口和业务扩展留在产品侧。

2—3 分钟口述版本 ​

面试官您好，我介绍一下探迹销售 AI Agent 项目。

这个项目服务于企业销售场景。公司有 Sales、Tuoke 等多个业务产品，过去用户主要通过表单和业务页面完成筛选、分析和后续操作。引入 Agent 后，用户可以用自然语言描述目标，由 Agent 分析需求、调用工具并返回结果。

项目的难点不在于把一个输入框接到接口，而在于 Agent 的一次执行会持续产生多个阶段和多种类型的事件：可能有文本增量、工具调用、文件展示、等待用户确认和最终结果。前端需要把这些持续到达的网络数据转换成稳定的会话状态，同时让用户看见任务正在进行到哪一步。

第二个问题是能力复用。Sales、Tuoke 等产品都需要流式会话，如果每个产品分别实现 SSE 解析、消息归并、请求取消和会话管理，协议变化和问题修复都会重复发生。因此项目采用公共能力下沉、业务差异上移的方式，把通用逻辑集中到 agent-core，产品侧负责接口适配、鉴权和业务扩展。

用户发送消息后，产品侧先整理文本、附件和模式等参数，并在本地插入用户消息，让界面立即反馈。首次发送时先创建或确定会话，随后由 client 发起 POST Fetch 请求，通过 ReadableStream 接收服务端持续返回的数据。

读取时不能把每个 chunk 直接当成一条消息。一个中文字符可能跨越两个 chunk，一条 SSE 事件也可能被拆开，所以公共层先使用 TextDecoder 增量解码，再用字符串缓冲按空行拼出完整事件，最后由产品协议层解释事件内容。

事件进入运行时后，会根据业务标识归并到已有记录。同一个事件后续收到文本或阶段更新时，更新原记录的内容和状态，而不是在列表中不断新增消息。工具调用和人工确认则映射到工具卡片或确认入口，界面需要区分执行中、等待操作、完成和错误等状态。

请求生命周期也需要单独管理。开始新执行、切换会话或组件卸载时，使用 AbortController 尽量停止旧连接，同时递增执行序号。异步回调真正提交状态前再检查序号，防止已经进入 JavaScript 回调队列的旧结果覆盖当前会话。

我主要参与 Sales 产品接入和公共 Agent 能力建设，具体个人职责需要以实际提交和参与范围为准。项目形成的价值是：复杂的流式执行过程可以在前端被持续展示和交互，多个产品也可以共享同一套协议处理与会话基础能力。

关于断线恢复，我会把连接重试、任务恢复和消息游标重放分开说明。当前材料可以确认流解析、事件归并和前端执行隔离；是否具备消息级游标恢复，要以服务端事件保留、游标字段和对应测试为证据，不能只因为使用了 SSE 就直接称为断点续传。

网络层和业务层的身份不要混为一谈：

text
conversationId = 多轮对话的归属

messageId      = 一条展示消息的归属
event_id       = 业务事件或展示实体的标识，是否等于传输游标要看协议
sequence       = 前端某次连接的执行身份
AbortSignal    = 当前网络读取的取消信号

最值得讲的两个技术问题 ​

1. 从字节流到稳定会话状态 ​

现象： ReadableStream 每次读取的 chunk 边界由网络决定，不能代表字符、SSE 帧或业务消息的边界。

处理链路： TextDecoder.decode(value, { stream: true }) 负责保留不完整的 UTF-8 字节；字符串 buffer 负责保留不完整的文本帧；空行分帧后，再由协议层解析 event 和 data。

状态归并： 解析后的事件进入 eventStore 或等价的归并层，以稳定业务标识定位记录。对象字段可以按协议合并，数组是整体替换还是增量追加必须由协议定义。

边界： event_id 是业务标识时，不能自动当成消息游标；字符串 delta 是否可以重复追加，也不能只靠前端去重推断。乱序版本拒收、服务端副作用幂等和事件重放需要独立证据。

2. AbortController 与执行序号 ​

现象： 用户可能连续发送消息、切换会话或卸载页面。旧请求的网络回调、解析逻辑和 finally 可能与新请求交错。

处理方式： AbortController 负责取消不再需要的网络读取，执行序号负责判断结果是否仍属于当前 run。每个关键回调都检查当前序号，旧 run 的完成和错误只能清理自己的状态。

为什么不能只用 abort： abort 不能撤销已经完成的 Promise，也不能保证已经排入 JavaScript 队列的后续逻辑自动消失。资源取消和状态提交资格是两个问题。

边界： 这能保护前端连接和展示状态，不能等同于服务端任务已经停止；服务端是否取消执行，需要单独的取消协议。

高频追问与回答 ​

1. 为什么要做 Agent？传统业务系统不够用吗？ ​

Agent 不是替代原有业务系统，而是补充一种任务交互方式。传统页面适合用户目标明确、知道应该点击哪些功能的场景；复杂业务中，用户可能只知道目标，不清楚应该组合哪些条件。Agent 可以用自然语言理解意图，并结合业务工具执行任务。对前端来说，变化是从展示一次响应，变成展示一个持续执行的过程。

2. 为什么抽取 agent-core，直接做一个聊天组件不行吗？ ​

复用的重点不是聊天外壳，而是会话生命周期、流式协议处理、消息归并、请求取消和通用消息展示。如果只抽一个 UI 组件，产品仍然会重复实现这些运行时能力。agent-core 下沉协议和会话共性，产品侧保留接口、鉴权、CRM 操作和工具扩展，因此公共模块不会依赖某个产品的业务规则。

3. 为什么使用 SSE，而不是 WebSocket？ ​

当前交互是用户提交一次请求，服务端在任务执行过程中持续向前端返回多个事件，通信方向主要是服务端到客户端，因此 SSE 更贴合场景。项目使用 Fetch + ReadableStream，是因为请求需要 POST body、业务鉴权和主动取消。WebSocket 也可以实现，但会引入长连接和双向消息协议管理；如果未来需要高频双向协作，再重新评估。

4. SSE 解析的难点是什么？ ​

难点有两个。第一，chunk 不等于字符或事件，需要增量解码和缓冲分帧。第二，解析出事件后不能直接追加 UI，因为同一业务事件可能持续更新，需要按稳定标识归并。还要明确多行 data、换行格式、空帧、EOF、错误响应和事件终态的处理规则。

5. 既然有 AbortController，为什么还需要执行序号？ ​

AbortController 主要负责停止网络读取，执行序号负责验证结果写入资格。旧请求可能已经拿到数据，或者 Promise 已经进入回调队列，此时 abort 不能撤销后续 JavaScript 逻辑。新执行递增序号，旧回调发现序号不匹配就丢弃，因此两者分别解决资源释放和状态一致性。

6. agent-core 与 Sales 的边界怎么划分？ ​

跨产品都需要、且不依赖具体业务的能力放进公共层，例如 SSE 解析、会话管理、事件归并和通用消息渲染。接口地址、鉴权信息、CRM 写入确认、连接器和产品专属卡片放在 Sales。公共层依赖协议和扩展接口，产品层负责把自己的业务差异接入。

7. 如果未来新增 Vue 3 产品，能直接复用吗？ ​

当前不能保证全部直接复用，因为 agent-core 中包含 React Hooks 和 React UI。更合理的演进是拆成框架无关的协议与运行时核心，再为 React、Vue 分别提供订阅和组件适配层。但是否值得拆分，要看真实接入需求和维护成本，不能为了预想场景提前重构。

8. 这套系统最能体现你的技术能力在哪里？ ​

一是把网络分块、协议解析、事件归并和 UI 状态连接起来，处理复杂异步流程；二是参与公共模块边界设计，让多个产品共享会话能力，同时把业务差异留在产品侧。具体使用“我设计”“我实现”还是“我参与”，需要与实际职责和提交记录一致。

9. 流式输出中途断网怎么办？ ​

我会先区分三层能力：重连是重新建立连接，任务恢复是继续关联原来的服务端任务，消息级恢复是根据游标补发遗漏事件。前端现有的取消和执行序号可以防止旧连接污染当前状态；要称为消息级恢复，还必须有服务端保留事件、游标字段、重放接口和重复事件处理证据。如果这些条件没有确认，面试时应回答“具备前端连接隔离，恢复能力取决于服务端协议”，而不是直接说已经实现断点续传。

面试前的事实核对 ​

  • agent-core 中哪些文件是本人亲自设计或修改的？
  • 是否实际参与了 SSE 解析、事件归并或请求隔离的实现？
  • 服务端是否提供 seq、cursor、事件重放或任务状态查询？
  • 工具调用的副作用由哪一层保证幂等？
  • 是否有测试覆盖 UTF-8 跨块、事件跨块、旧 run 回调和终态收敛？
  • 是否有性能或接入成本数据可以引用？

没有证据时，优先使用“当前实现采用”“项目中参与了”这样的表达，并把拟议改进单独说明。
