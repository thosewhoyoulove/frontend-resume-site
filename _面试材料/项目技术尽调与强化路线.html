2. 高级筛选与智能搭建 ​

一句话价值：将 AI 生成条件接入存量复杂筛选系统，在模式、视图、配置和长任务交错变化时维护查询语义，并复用已有结果。

核心架构与数据流 ​

自然语言输入 → POST Fetch SSE → 阶段事件/任务结果 → 校验 ready 与条件对象 → applyFilterSnapshot → DimensionSelector 回填与容器状态更新 → 携条件快照查询 → 表格或卡片结果。

状态并非全部进入 Redux：Redux 提供配置、用户与权限等上下文；容器本地 state 保存条件、分页、结果和 loading；实例字段维护提交时的 filter/relation 与待处理查询；用户存储保存分模式条件、结果元信息及任务快照。需要讲清楚每一层的生命周期，而非简单说“Redux 统一管理复杂状态”。

F1｜模式隔离与条件快照回填〔A〕 ​

难点： 普通筛选与智能搭建共用筛选器，生成结果还可能早于维度配置到达；仅先 setState 再读取旧状态，容易查询错误条件。

实现： 普通条件与 smartBuild 条件分仓；applyFilterSnapshot 更新容器并驱动选择器，再把同一份条件传给 handleFilterSnapshotSearch。配置未到时 setValue 写入 pendingValue，配置到达后转换；关系值 0/1 单独判断，不能按真假值丢失 0。

可证明收益： 统一了智能结果应用入口，并为配置晚到提供延迟回填路径。它解决的是特定时序和状态归属，不等于已建立完整事务或消除所有竞态。

代价： 容器 state、选择器内部状态、实例字段存在同步成本；代码仍混合旧生命周期与命令式 ref 调用，后续可以沿清晰契约逐步收敛。

证据：工作区分仓与快照应用、配置到达后回填、pendingValue、快照查询入口。

F2｜双视图结果复用与查询协调〔A，保证范围为 B〕 ​

难点： 卡片与表格接口和分页语义不同；反复切视图容易重复获取相同结果；旧请求尚未结束时用户可能提交新条件。

实现： 两类视图分别保存数据、分页、loading、已查询标志和查询键。查询键包含条件、关系、分页、排序和 mode，切视图先判断键是否匹配，再决定是否请求。handleFilter 在 loading 期间保留最新待查条件，两个 loading 都结束后由 componentDidUpdate 触发后续查询；这是单槽最新请求合并，不是保存全部操作的 FIFO 队列。

可证明收益： 已完成结果且查询键匹配时，切换回视图可复用结果；忙碌期间新的筛选意图有明确的续查路径。可以写“结果复用、减少该场景重复请求”，不能写“全局请求去重、通用请求缓存”。

边界： hasFresh... 的 fresh 仅指参数键匹配，没有时间新鲜度；并未证明服务端数据未变化。切视图等入口直接调用取数方法，不能由 handleFilter 的 loading 门禁推导所有入口都串行。取数回写没有统一 generation 校验，重叠请求的旧成功、旧失败、loading 清理仍需故障注入验证。

证据：忙碌结束后续查、查询键、单槽待查条件、切视图结果复用。

F3｜任务级恢复与流隔离〔A，恢复可靠性为 B〕 ​

难点： 页面离开后连接会中断，但后端任务可能仍在运行；重新进入既不能盲目创建任务，也不应重播全部已完成动画。

实现： 按用户和主体保存 taskId、输入、startedAt 和阶段快照；恢复时携 taskId 续接，跳过已完成阶段展示；开始新任务或卸载时失效请求序号并 abort。任务缓存以任务开始时间计算五分钟最大年龄，不是每次写入后续期五分钟。嵌入模式禁用任务缓存。

可证明收益： 正常页面离开后，在有效期内具备重新连接同一任务、恢复阶段展示的前端路径；嵌入宿主有独立恢复策略。

边界： 这不是消息游标级断点续传，也没有证明任意断网都会自动重连。浏览器 abort 不等于服务端任务终止。任务是否保留、权限变化后是否可恢复，需要服务端契约与联调。

证据：任务缓存与年龄限制、卸载快照与请求失效、新任务序号和恢复展示、重新进入续接。

F4｜将生成任务接入可编辑、可保存的业务闭环〔A〕 ​

难点： AI 输出的展示文本不能充当筛选条件；阶段完成、结果可用、动画结束、业务回填是不同事件。

实现： POST SSE 区分阶段、结果、错误，并检查 HTTP 状态与流类型；容器以 ready + 条件对象判断是否应用；使用同一套既有条件编辑、保存与分享能力。界面展示队列与结果应用有显式衔接。

可证明收益： 智能生成产物可进入现有业务操作链路，而不只是独立聊天展示。没有操作埋点对比时，不写“效率提升 XX%”。

边界： 对象类型检查不是完整业务 schema 校验；合法字段、操作符、枚举值和权限仍需前后端共同校验。展示队列也不应长期阻塞业务终态提交，值得区分任务状态与动画状态。

证据：POST SSE与流解析、结果对象检查、应用结果的判断。

优先核实与升级 ​

B：外部回填时的旧回调。 SmartBuilder 外部结果同步分支 abort 旧流并释放展示队列，但没有同步递增 requestId；旧 Promise 已完成且等待展示时，abort 无法撤销后续 .then。这是静态可达风险，尚未在完整页面复现。另有 onTaskId 在 shouldCancel 检查前改写 ref，宜纳入同组用例。外部回填分支。

B：页面缓存不等于请求缓存。 RuntimeCache 保存整页状态；调用传入字符串形式的 expireKeys 和第四参数，但实现读取对象的 item.expire，且只接收三个形参。不能据此宣称 TTL 请求缓存。调用、实现。

C：优先做统一的查询提交与结果接受规则。 将 committed snapshot 与 UI 草稿分离；每个结果槽使用 generation，请求完成的 success/error/finally 都验证归属。模式或主体改变应失效关联请求。先保留旧组件，仅抽取纯函数及控制器，降低重写成本。

C：再做可解释的请求缓存。 queryKey 明确 tenant/user/权限版本、主体、查询模式、视图/API 版本、规范化条件、分页与排序；补充 in-flight 去重、结果 TTL、容量上限、写操作后的失效。多个调用者复用请求时，用订阅者引用计数管理 abort，避免一个调用者取消拖垮其他调用者。不要未经协议允许排序有业务语义的条件数组。

C：任务恢复升级。 与后端约定任务状态查询、保留期、事件 seq/cursor、重放去重和明确终态；断线先确认任务状态，再决定回放或重新发起。建立有限重试、抖动退避与可观测恢复失败原因。前端不能独自保证 exactly-once。

3. 营销触达 SDK ​

一句话价值：将呼叫业务、响应式状态和跨宿主通信分离，使多业务页可以通过统一接口接入共享呼叫状态，并在受限环境保留单页能力。

核心架构与数据流 ​

业务 UI / Model → BLL 业务操作与 vm 更新 → Bridge 汇总变更 → Bus → 隐藏 iframe → SharedWorker 的 MessagePort → coreLogic 更新共享缓存并广播 → 页面 Bridge 使用 noWatcherSet 更新本地模型 → 通知 UI。

要强调两条不同链路：业务命令经 action 到核心逻辑；状态同步经 keys/concat 回到视图。不能把所有消息都理解为任意远程函数调用。

S1｜职责分层与避免同步回环〔A〕 ​

难点： 呼叫动作、状态显示、宿主差异交织，跨页收到的状态如果再次作为本地变更广播，会形成回环。

实现： Model 组合 BLL 与 Bridge；Bridge 基于观察模型聚合本地修改，在定时器批次发送 keys；接收广播使用 noWatcherSet 更新，随后通知视图，区别本地写与远端回放。

收益与代价： 状态同步规则集中，UI 不直接处理底层端口；代价是自研 Proxy/观察机制、命令式 vm 与 React 的联动增加调试和维护成本，分目录本身并不意味着完全低耦合。

证据：Model组合、接收广播、聚合发送、静默写入。

S2｜iframe桥接与共享状态生命周期〔A，可靠性为 B〕 ​

难点： 不同宿主页要通过 SDK 资源域的桥接页面接入共享上下文，新页面还需要初始化快照。

实现： Bus 创建隐藏 iframe、加载前暂存消息；桥接 iframe 创建 SharedWorker；worker 保存 tabId、端口 Map 与共享状态，新页面读取快照，状态改变后广播；beforeunload 时清理页面登记。

可证明收益： 支持新页面初始化与已连接页面的状态传播，业务侧复用桥接抽象。存在 ping 与失联标记机制，但没有证据支持端口失败自动恢复、持久化可靠投递或浏览器关闭仍保持通话。

边界： onHangupPhone 和 beforeunload 清理代码明确存在，不能将其包装成“关闭当前 Tab 通话无缝迁移”。SharedWorker 的可共享范围受同源要求及浏览器隔离策略约束；不能写任意跨域 iframe 可直接共享。SharedWorker 文档。

证据：iframe加载与缓冲、桥接方向、worker端口、共享缓存、退出清理。

S3｜同接口、不同能力的兼容实现〔A〕 ​

难点： 宿主不能使用 SharedWorker 时，业务不应被迫重写呼叫入口，但不能虚构跨页能力仍然存在。

实现： createBus 检测 SharedWorker，缺失时动态导入 CompatibleShareBus；通过 ImitateBridge / ImitatePort 在当前 JS 上下文复用 dealBussinessEvents，与正常分支共同继承 BusAbstract。

可证明收益： 业务通信接口及核心处理逻辑可以复用；降级路径维持单页调用。它不是 BroadcastChannel 降级，也不是跨 Tab 共享降级。

边界： 检测 API 存在不能覆盖 worker 创建失败、CSP、脚本加载失败等场景；当前有关闭标志，未见这些失败统一转入兼容分支。模拟端口同步执行回调，真实端口异步投递，两种调度语义也应做契约测试。

证据：分支选择、兼容Bus、进程内端口。

优先核实与升级 ​

B：通信安全。 bridge iframe 的来源校验使用 /.*tungee.com/ 等宽松匹配；本轮本地实验确认它接受带合法域字符串的无关域名。页面侧 BusAbstract.receiveMsg 未在该入口校验 origin/source；部分发送使用 *。这是代码层的信任边界缺口，不代表已在实际宿主复现越权。来源检查、页面收信。

C：通信协议加固。 从配置建立精确 origin allowlist；验证 event.source === 预期窗口，发送使用明确 targetOrigin；用运行时 schema 校验协议版本、消息类型、字段大小、requestId、身份上下文。不要把 TS 类型当运行时校验。业务权限仍由服务端校验；nonce 不能替代 origin/source。postMessage 安全要求。

B/C：请求关联与资源释放。 getStorage 只使用单个 tmpCallback 槽，若存在并发请求可能覆盖；全局 message 监听以 bind 新函数注册，未在本次入口看到配套 dispose。建议增加 requestId→pending Map、超时清理、统一 dispose，以及重复初始化、卸载和用户切换测试。不要在未证实并发调用前断言线上已经丢响应。

C：显式能力协商。 对外暴露 shared-state / single-page 等能力和失败原因；握手超时后决定降级或可恢复错误。只有确实需要跨 Tab 降级时再评估 BroadcastChannel + leader/lease；它只提供广播，不自动提供中心状态、选主和单次业务执行。呼叫、写入等副作用仍要服务端幂等。

4. AI Agent ​

一句话价值：将字节流解析、业务事件归并、会话生命周期与产品扩展拆开，使流式交互在多产品共享内核上可维护、可测试。

核心架构与数据流 ​

产品 client 调用统一 request → Fetch body 字节流 → TextDecoder → SSE data parser → 产品协议 payload → useAgentSessionStream 检查 run 有效性 → eventStore 归并 → 会话状态映射 → ConversationStream 分段与扩展组件渲染。

AgentProvider 注入 client、manifest、registry、components、voice；workspace 中的 sales / tuoke 各自依赖 @tungee/agent-core，并有独立构建入口。协议层、runtime、React hooks 与产品接口适配的分离是实际存在的，不只是文件夹命名。

A1｜字节解码与事件分帧分层〔A，标准覆盖为 B〕 ​

难点： 网络 chunk 不等于字符，也不等于完整事件。中文可跨字节块，事件可跨块或同块多帧。

实现： TextDecoder.decode(..., { stream: true }) 保留不完整字符；字符串 buffer 保留不完整帧；解析多行 data、注释及常见换行；产品 client 再解释业务 payload。读结束 flush decoder，并释放 reader lock。

可证明收益： 避免把网络分块直接作为业务事件。现有测试通过；本轮中文/emoji样本全部 33 个单切点通过。这个数据只描述样本验证，不能写成线上成功率。

限制： 这是面向业务 data 的解析器，不完整实现 SSE 的 id/event/retry 与自动重连。混合 LF/CRLF 的空行在实验中被归并成同一事件；EOF 无结束空行时主动发出尾帧，与标准处理不同，现有测试却明确要求该兼容行为。应先确认服务端契约再调整，不能直接把旧行为当作完整标准支持。HTML SSE 标准。

证据：SSE解析器、流读取、产品请求适配。

A2｜稳定标识、字段合并与历史归一化〔A，乱序幂等为 B〕 ​

难点： 同一条业务事件会持续更新；子任务的不同阶段可能使用不同 event_id；历史记录和实时流需得到一致的展示结构。

实现： 普通事件以 event_id/_id 为键；map_subtask 使用 map_id + index；Map 保存位置索引，重复键合并字段。对象递归合并、数组整体替换、undefined 保留旧值；对子任务 input_preview 做保留规则；历史和实时分别通过 normalize/upsert 使用相同逻辑。

收益与代价： 多阶段进度可更新同一条目，历史重放可归一化。Map 减少定位扫描，但数组复制和深合并仍有成本；不能称整体 O(1)。需要依赖服务端确认字段是快照还是 delta。

限制： 合并没有版本顺序检查，实验中旧版本会覆盖新内容；没有键的事件无法按键去重。event_id 是业务标识，不自动等于 SSE cursor，也不意味着业务副作用幂等。

证据：事件键、字段语义、实时upsert。

A3｜连接取消与回调失效〔A，业务状态机为 B/C〕 ​

难点： 会话切换后旧回调可能继续到达；旧请求 finally 也可能错误清除新请求状态。

实现： streamController 的 begin 取消前一个 run 并递增 sequence；回调检查 isCurrent；finish 只清理自己对应的 run。useAgentSession 在切会话与卸载时 stopStream。现有测试覆盖 begin/stop，本轮额外验证旧 finish 不清除新 run。

可证明收益： 当前 run 才能提交事件，连接资源与业务提交资格分别管理。相比只有 abort，更能处理已经进入 JS 回调队列的旧工作。

限制： 当前 session.js 是事件到状态的映射：error/done/insufficient 都映射 completed，wait→waiting，其余→running；没有完整合法迁移表、终态吸收或未知事件拒绝，不能称为完备状态机。流控制隔离也不能代替服务端任务取消。

证据：控制器、回调保护、切会话与卸载、当前状态映射。

A4｜共享内核与产品扩展〔A，性能收益为 B〕 ​

难点： sales / tuoke 共用会话与展示能力，但接口、工具卡片、品牌和宿主不同；复制页面会导致协议与交互分叉。

实现： workspace 共享 core/host-bridge；产品通过 client + manifest + extension registry 接入；扩展点包括 eventRenderers、waitHandlers、composerItems、sidePanels、toolPresenters，按注册顺序匹配。ConversationStream 将扁平事件整理为展示段落，含工具/任务归并。

可证明收益： 公共事件和生命周期逻辑有统一维护位置，产品差异有注入入口。代码证明复用结构，不证明接入时间缩短了某个百分比。

限制： useMemo 依赖的 events 每次改变时仍会重建索引和分段；不能仅凭 useMemo 声称长会话高性能。AgentProvider 还通过模块级 agentFileClient 配置文件 client，同一模块实例下并存多个 provider 时可能互相覆盖，需要隔离测试。

证据：workspace、Provider注入、扩展注册表、分段构建、文件client全局槽。

值得落地的升级 ​

C：协议与状态收敛。 明确事件 envelope 的 sessionId/runId/entityId/seq/schemaVersion，以及 snapshot、delta、terminal、error 的含义；reducer 校验合法迁移，区分 completed、failed、cancelled、waiting。terminal 后迟到的进度不能重新拉回 running；新 run 必须拥有新身份。版本机制需要后端配合。

C：增量展示性能。 先测量，再评估事件批处理、稳定事件引用、细粒度订阅、可见区渲染和长文本局部更新。终态、确认操作应及时 flush；后台页 requestAnimationFrame 可能节流，不能把唯一提交机制挂在动画帧上。虚拟列表需处理动态高度、底部跟随、历史定位与用户手动滚动，不应为技术名词强行引入。

C：多实例共享包。 把 file client 从全局变量改为实例依赖；增加两个不同 client 的 provider 并存测试、产品契约测试、包导出边界检查，再谈进一步扩大产品接入。

6. 测量方案：没有证据的收益不补数字 ​

  • 高级筛选： 固定条件 A/B、固定分页和数据快照，记录 card→table→card 的实际业务请求数；分别统计缓存可复用场景与条件变化场景。增加响应乱序/500/取消，观察是否错写结果和提前结束 loading。
  • 智能搭建： 定义创建→ready、ready→可用结果、离页→重入恢复等时间点，统计恢复成功率及失败分类；分母仅包含有效任务与可恢复场景，区分五分钟失效和服务端失败。
  • SDK： 记录命令发送至目标页收到状态的 p50/p95、初始化耗时、消息数量、长期运行 listener/port 数；分别测正常共享与单页降级，不能混报平均值。
  • Agent： 固定事件轨迹和速率，覆盖 100/1000/10000 条规模；记录 React commit 次数、actualDuration、长任务、堆内存和输入响应。采用相同机器、同一构建模式、重复运行及分位数；开发模式结果不冒充生产性能。React Profiler。
  • 千瓦构建： 原稿“60s→15s”是历史自述，本轮无旧项目和原始日志。要恢复数字，补充前后 commit、同机硬件、Node/依赖版本、构建命令、冷/热缓存口径和多次采样结果；不要把构建耗时和启动耗时混用。

7. 推进顺序 ​

  1. 先掌握本报告 11 条 A 类亮点的代码链路，用配套训练稿检验是否能解释代价与边界。
  2. 优先修复小而明确的问题：智能搭建统一失效入口、SDK origin/source 校验、SSE边界契约。每项先写可复现失败用例再修改。
  3. 再落地查询协调控制器与请求缓存；用请求计数和乱序测试证明收益。
  4. 最后推进 Agent 性能与多实例隔离；先保存基线，再选择改动，避免只堆状态机、虚拟列表等术语。
