企业级高级筛选与 AI 智能搭建 · 背诵版 ​

用途：回答“介绍一下这个项目”“你在这个项目中解决了什么问题”“AI 结果如何进入原有业务系统”。建议先背第一部分的 2—3 分钟版本，再按追问展开。

一句话先说清楚 ​

这是一个把自然语言生成的筛选条件接入存量企业检索系统的复杂业务模块，核心是处理条件归属、配置时序、双视图查询和长任务生命周期。

一、先记住这句话 ​

我参与的是一个把自然语言生成结果接入企业高级筛选系统的复杂业务模块，重点解决 AI 任务、筛选器配置、双视图结果和页面生命周期同时变化时，条件归属和查询结果保持一致的问题。

面试官继续追问时，围绕三个词展开：

  1. 条件归属：普通筛选和智能搭建的条件要分开保存。
  2. 条件一致：界面回填的条件和实际查询提交的条件要来自同一份快照。
  3. 任务生命周期：流连接、后端任务和页面缓存是不同层次，不能混为一谈。

二、2—3 分钟口述版本 ​

面试官您好，我介绍一下企业级高级筛选与 AI 智能搭建项目。

这个项目面向企业客户检索场景。用户原来需要在高级筛选页面里逐项选择行业、地区、规模等条件，再查看企业结果。项目增加智能搭建后，用户可以直接用自然语言描述目标客户，系统通过 AI 生成筛选条件，然后继续使用原来的条件编辑、企业查询、保存条件组和分享能力。

它和普通 CRUD 页面相比，复杂点不在于多几个表单字段，而在于多个异步过程会同时发生：AI 条件生成是一个持续返回阶段事件的长任务；筛选维度配置也是异步加载的；页面还同时支持普通筛选和智能搭建，以及卡片和表格两种结果视图。用户还可能在任务执行中离开页面、切换主体或切换结果视图。

我先讲一次完整流程。用户输入自然语言后，前端通过 streamAdvancedFilterAgentBuild 使用 POST Fetch 接收 SSE 流。读取响应时，先用 TextDecoder 做增量解码，再用字符串缓冲按照空行拆分 SSE 帧，解析阶段、结果和错误事件。任务执行过程中，页面展示阶段进度，并保存服务端返回的 taskId。

当任务返回 ready 状态并且存在有效的条件对象时，前端才把结果交给筛选系统。这里不会直接把结果塞进某个组件，而是通过 applyFilterSnapshot 统一更新容器里的条件、关系和值回填，再把同一份条件快照传给 handleFilterSnapshotSearch 发起查询。这样可以减少 React 状态更新还没有完成时，查询读取到旧条件的风险。

条件回填还有一个时序问题。DimensionSelector 需要先拿到维度配置，才能把接口格式转换成界面可以编辑的结构。如果 AI 结果先返回，配置还没有加载完成，代码会先把值放进 pendingValue；等配置到达后，再优先转换这份待回填值，避免空的默认值把 AI 条件覆盖掉。关系值还要区分 0 和 1，不能简单用真假值判断。

在结果展示上，卡片和表格分别保存自己的数据、分页、loading、是否查询过以及查询键。切换视图时，前端会根据筛选条件、关系、分页、排序和模式生成查询键；如果目标视图已有相同查询键的结果，就可以复用，否则再请求。用户在请求进行中再次修改条件时，当前实现只保留最新一份待查条件，等正在进行的查询结束后继续执行。

长任务方面，普通页面会按用户和主体保存 taskId、输入文本、开始时间和阶段快照。用户在有效期内返回时，可以带着同一个 taskId 重新连接，并直接展示已经完成的阶段。任务有效期是从开始时间计算的五分钟。嵌入到其他宿主的场景会关闭这套页面缓存，避免不同宿主之间复用错误任务。

请求控制上，AbortController 负责取消旧的流连接，requestId 负责判断回调是否仍属于当前这次执行。因为取消连接不代表已经进入 JavaScript 回调队列的代码一定不会继续执行，所以两者解决的是资源释放和结果提交资格两个不同问题。

我在这个项目中重点参与了高级筛选和智能搭建相关的前端开发，具体负责范围需要结合实际改动进一步确认。代码层面可以确认的是：项目已经形成了从自然语言输入、流式生成、条件回填，到企业查询、人工编辑、保存和分享的完整前端链路。没有线上埋点或对比数据时，我会把收益表述为“形成了可复用、可追踪的闭环”，不会编造效率提升比例。

请求身份需要单独理解：

text

四、最值得深入的五个模块 ​

1. AI 结果进入既有筛选闭环 ​

代码证据： api.js 中的 streamAdvancedFilterAgentBuild、getAdvancedFilterAgentBuildFilter；SmartBuilder/index.js 中对 ready 和条件对象的检查；EnterpriseFilter.js 中的 handleFilterSnapshotSearch。

为什么值得讲： 这体现的不是“调用 AI 接口”，而是把不确定的生成过程接入已有的确定性业务流程。生成结果还需要继续被编辑、查询、保存和分享。

核心设计： 阶段展示状态、任务完成状态和业务条件可用状态分开判断。只有任务 ready 且条件对象满足基础结构检查时，才进入统一回填入口。

边界： 对象存在不等于完整业务校验已经完成；操作符、枚举值、权限仍需要服务端和前端共同保证。当前实现也不能证明具备消息游标级断点续传。

2. 条件快照与异步回填 ​

代码证据： utils.js 中的 resolveWorkspaceFilter、pickFilterSnapshot、applyFilterSnapshot；DimensionSelector/index.js 中的 pendingValue、setValue 和配置更新逻辑。

为什么值得讲： 条件回填同时影响容器状态、筛选器内部状态和查询参数。只依赖某个组件“当前最新 state”，容易把不同时间点的数据混在一起。

核心设计： 用工作区分离普通条件和智能条件；用快照统一更新展示和查询；配置没准备好时先暂存原始条件，配置到达后再转换。

边界： 这是针对配置时序和状态归属的处理，不等于建立了完整事务，也不等于所有异步竞态都已消除。

3. 普通筛选与智能搭建的工作区隔离 ​

代码证据： resolveWorkspaceFilter 根据 isSmartBuild 读取普通工作区或 smartBuild 工作区；EnterpriseFilter 保存当前条件、模式和查询结果；用户存储按用户保存高级筛选数据。

为什么值得讲： 用户可能先配置普通筛选，再进入智能搭建；如果两套条件共用一个可变对象，切换模式时容易覆盖用户正在编辑的内容。

核心设计： 把条件归属和模式状态作为独立维度保存。嵌入场景还可以通过 suppressSmartCache 关闭智能条件缓存恢复。

边界： 代码证明了工作区分仓和缓存读取路径，不能据此声称所有状态都由 Redux 统一管理；结果、分页和 loading 主要位于页面本地 state。

4. 卡片 / 表格双视图与查询协调 ​

代码证据： EnterpriseFilter 中的 tableData、cardData、loading、cardLoading、分页字段、getCardSearchKey、getTableSearchKey、pendingFilterSearch 和 componentDidUpdate。

为什么值得讲： 两种视图接口和分页语义不同。简单做法是切换视图就重新请求，或者让两个视图共用 loading 和结果，都会增加重复请求或状态相互覆盖的风险。

核心设计： 两个结果槽分别维护数据和查询键；查询键包含条件、关系、分页、排序和模式；请求忙碌期间只保留最新待查询条件，结束后继续查询。

边界： 这是页面内的结果复用，不是带 TTL 的通用请求缓存，也不是 FIFO 操作队列。查询键匹配只说明请求参数语义一致，不代表服务端数据一定仍然新鲜。

5. 任务恢复与流连接失效 ​

代码证据： SmartBuilder/index.js 中的 requestIdRef、abortControllerRef、shouldCancel、卸载清理和恢复逻辑；taskSession.js 中按用户和主体读写任务、五分钟有效期和清理逻辑。

为什么值得讲： 页面生命周期和服务端任务生命周期可能不同。页面离开会导致浏览器连接结束，但后端任务未必已经结束。

核心设计： 保存任务身份和阶段快照，返回时用原 taskId 重新连接；通过 requestId 拦截旧回调，通过 AbortController 取消旧流；嵌入场景禁用页面级任务恢复。

边界： 这是任务级恢复，不是消息游标级断点续传；也不能仅凭前端 abort 证明服务端任务被取消。外部结果回填分支是否覆盖所有旧回调边界，仍需要运行验证。

五、Before / After ​

这里的 Before 分为两类：源码没有保留的历史实现不能当作事实；下面“简单替代方案”是为了说明设计权衡的合理推演。

场景一：AI 结果回填筛选器 ​

简单替代方案： 收到 AI 结果后直接 setState，再从组件当前 state 读取条件发起查询。

可能的问题： React 状态更新和筛选器内部配置转换不一定在同一时刻完成；查询可能读取旧条件，或者配置尚未加载时把条件转换成空值。

当前实现： applyFilterSnapshot 同时接收条件和关系，更新容器并驱动 DimensionSelector；查询入口直接使用这次传入的快照。配置未到时由 pendingValue 暂存。

可以确认的变化： 生成结果有明确的回填入口，配置晚到有明确的等待位置，回填和查询使用同一份输入。

场景二：卡片与表格来回切换 ​

简单替代方案： 两个视图共用一套结果和 loading，切换时无条件重新请求。

可能的问题： 卡片和表格的分页、排序、接口字段不同；切换时可能覆盖彼此的 loading 或结果，且相同条件下产生重复请求。

当前实现： 两个视图分别保存结果、分页、loading、查询标记和查询键；命中相同查询键时复用对应结果。

可以确认的变化： 页面具备该场景下的结果复用和状态隔离路径；没有证据支持“所有请求都已去重”或“数据始终实时”。

场景三：用户离开后返回 ​

简单替代方案： 离开页面就丢弃流，返回后重新创建一个任务。

可能的问题： 长任务可能被重复创建；用户看不到已经完成的阶段；如果服务端任务仍在运行，前端与服务端任务会失去关联。

当前实现： 普通页面保存 taskId、输入、开始时间和阶段快照，五分钟内返回时续接原任务；恢复时跳过已完成阶段。嵌入场景关闭这套缓存。

可以确认的变化： 页面返回存在任务级续接路径；恢复范围和嵌入场景边界是明确的。

六、STAR 面试回答 ​

S：背景与问题 ​

企业高级筛选页面本身已经有较多条件维度、条件组合、保存和结果操作。新增智能搭建后，用户可以输入自然语言，但 AI 生成是流式长任务，筛选器配置又是异步加载的，同时页面还支持普通筛选、卡片视图和表格视图。多个状态如果没有明确归属，就可能出现条件显示和实际查询不一致、切换视图重复请求或离开页面后任务无法继续的问题。

T：职责与目标 ​

我的目标是参与完成智能搭建结果与既有高级筛选系统的衔接，让生成条件能够被筛选器正确回填，并继续支持企业查询、手工调整、保存条件组和分享。同时需要处理流连接取消、页面返回任务恢复以及不同宿主的生命周期差异。

这里“我独立设计了全部架构”这一表述需要本人确认。当前源码只能证明这些机制存在，不能单独证明每一处都是我提出或独立完成的。

A：技术方案与落地 ​

  1. 在流接口层使用 POST Fetch 接收 SSE，增量解码并按空行拆分事件，区分阶段、ready 结果、错误和异常断流。
  2. 任务 ready 后先检查可用条件对象，再通过 applyFilterSnapshot 统一回填容器和筛选器。
  3. 配置未到时用 pendingValue 保存待转换条件，配置到达后优先恢复这份值，并单独处理关系值 0 和 1。
  4. 普通工作区和智能搭建工作区分别保存条件；卡片和表格分别保存结果、分页和 loading。
  5. 用查询键判断页面内结果是否可复用；请求忙碌时只保留最新一份待查询条件。
  6. 用 taskId 关联服务端任务，用 requestId 判断前端执行是否过期，用 AbortController 取消旧连接；普通页面保存限时任务快照，嵌入页面禁用缓存恢复。

R：结果与复盘 ​

从代码上可以确认，项目形成了自然语言输入、流式进度、条件回填、企业查询、人工编辑、保存条件组和分享口令的完整链路；也形成了配置晚到、视图切换和页面返回等场景的处理路径。

当前没有可直接引用的线上耗时、请求量、恢复成功率或用户效率指标，所以我不会编造百分比。下一步可以通过固定条件下的请求计数、任务恢复成功率、配置与结果不同到达顺序的用例，以及旧请求乱序回写测试来验证收益。

七、高频追问与背诵答案 ​

1. 这个项目和普通 CRUD 项目的主要区别是什么？ ​

普通 CRUD 主要围绕一次请求、一次响应和表单状态展开。这个项目有多个持续变化的状态：AI 流式任务、筛选条件草稿、已提交查询、卡片和表格结果、页面缓存以及用户编辑行为。难点是定义每个状态属于谁、什么时候可以提交、旧结果什么时候必须失效，而不只是把接口调用出来。

2. 为什么不能拿到 AI 总结文案后就直接搜索？ ​

总结文案只是展示内容，不一定是结构化、合法、可查询的条件。当前实现会检查任务状态是否为 ready，并通过 getAdvancedFilterAgentBuildFilter 检查条件对象的基础结构，然后才进入筛选器回填。完整的字段、操作符和权限校验仍然需要服务端和业务规则共同保证。

3. 为什么要使用条件快照？ ​

因为一次操作包含多个异步更新：容器要更新条件，筛选器要把接口格式转换成内部结构，查询又不能依赖某个时刻恰好读取到的可变 state。快照把“本次用户确认的条件”作为显式参数同时传给回填和查询，减少状态更新时序造成的隐式依赖。

4. setState 的回调已经执行了，为什么还需要快照？ ​

setState 回调只能说明当前组件这次更新完成，不能说明另一个筛选器组件的配置已经完成，也不能保证后续读取的 state 仍然代表这次操作。快照解决的是查询输入的明确归属，pendingValue 解决的是筛选配置尚未就绪，两者处理的是不同层次的问题。

5. pendingValue 解决了什么问题？ ​

DimensionSelector 需要配置才能把服务端条件转换为内部的维度结构。如果条件先到而配置后到，立即转换可能得到空条件，后续默认值还可能覆盖它。代码在配置缺失时先暂存传入值，配置到达后优先消费 pendingValue，再执行转换。这个机制解决的是“配置与条件到达顺序不同”的问题。

6. 为什么普通筛选和智能搭建要分开保存？ ​

它们是两个不同的用户工作区。用户可能在普通筛选里已经编辑了一组条件，再尝试智能搭建；如果共用一份条件，就需要额外处理覆盖和恢复。当前实现通过 resolveWorkspaceFilter 区分普通条件和 smartBuild 条件，页面缓存也按用户读取对应工作区。

7. 为什么卡片和表格要分别保存结果？ ​

两种视图使用的接口、字段、分页和排序语义不同。分别保存结果和 loading 可以避免切换视图时相互覆盖。查询键则进一步判断当前结果是否对应同一组条件、分页、排序和模式。它是页面内的结果复用，不是通用缓存系统。

8. 请求进行中用户再次点击筛选，为什么只保存最新一次？ ​

当前实现选择的是“最新意图优先”。用户连续修改条件时，中间每一次条件通常没有必要都执行；保留完整 FIFO 队列反而可能让页面继续执行用户已经放弃的条件。代价是中间操作不会逐个执行，而且它只覆盖了 handleFilter 这条入口，其他直接取数入口仍需要单独验证。

9. 为什么用 POST Fetch SSE，而不是原生 EventSource？ ​

这个接口需要提交自然语言输入和可选的 taskId，使用 POST 更符合请求协议；同时前端需要传递鉴权信息、接入 AbortController 并处理非 2xx 响应。原生 EventSource 更适合固定 URL 的单向订阅，对请求体和取消控制不够灵活。Fetch + ReadableStream 的代价是需要自己处理增量解码、分帧、错误和结束状态。

10. taskId、requestId 和 AbortController 分别解决什么问题？ ​

taskId 是服务端任务身份，用于页面返回后继续连接同一个任务；requestId 是前端本次执行身份，用于判断回调是否仍属于当前执行；AbortController 用于取消旧的网络读取。取消连接负责释放资源，执行序号负责阻止过期结果写入，服务端任务是否终止还要看后端协议。

11. 这是不是断点续传？ ​

只能称为任务级恢复，不能直接称为消息级断点续传。当前实现保存任务 ID 和阶段快照，返回页面后重新连接同一个任务，并跳过已经完成的阶段。没有足够证据证明保存了每条消息的游标、服务端支持事件重放，也没有证明任意断网都能自动恢复。

12. 如果没有这套实现，项目会是什么状态？ ​

历史旧实现需要以提交记录或当时的代码为依据，当前不能断言过去一定存在某个缺陷。作为简单替代方案，如果只在收到结果后直接更新 state 并查询，配置晚到、状态切换和查询输入归属会更依赖调用时序；如果切换视图始终重新请求，可能增加同条件下的重复请求。当前代码提供了快照、待回填、查询键和任务恢复这些明确路径，但收益仍应通过测试和业务数据验证。

14. 这个方案还有哪些不足？ ​

第一，查询结果回写没有在所有路径统一使用 generation 校验，重叠请求下旧 success、error 或 finally 是否会影响新请求，需要运行验证。第二，任务恢复不是消息游标级恢复。第三，条件对象的基础结构检查不等于完整 schema 校验。第四，页面本地状态、筛选器内部状态和缓存之间仍有同步成本。第五，查询键没有 TTL 语义，不能保证服务端数据实时。

八、面试官三级追问 ​

主题一：条件一致性 ​

第一层： AI 结果是怎么显示到筛选器里的？

答：任务 ready 后取得结构化条件，进入 applyFilterSnapshot，由它更新容器状态并调用 DimensionSelector.setValue。

第二层： 为什么不直接调用筛选器的 setValue？

答：只更新筛选器会让容器条件、查询条件和筛选器展示之间缺少统一入口。applyFilterSnapshot 先明确本次条件和关系，再决定只回填还是同时查询。

第三层： 条件先到、配置后到、用户又手工修改时，谁应该优先？

答：当前代码明确处理了配置未到时的 pendingValue，但用户编辑与异步结果之间的完整优先级规则需要结合实际产品约定和运行用例确认。更成熟的做法是给每次回填和用户编辑增加版本或 dirty 标记，明确旧结果是否还能覆盖用户输入。

主题二：查询复用 ​

第一层： 你们缓存了什么？

答：页面内缓存的是不同结果视图已经完成的结果和查询元信息，通过查询键判断是否可以复用。

第二层： 查询键包含哪些内容？

答：当前代码将条件、关系、分页、排序、业务排序和模式等信息组合成键。它表达查询语义，不代表数据有 TTL 或一定新鲜。

第三层： A 请求慢、B 请求快、A 最后返回怎么办？

答：这是当前需要重点验证的边界。pendingFilterSearch 处理的是筛选提交期间的最新意图，但所有结果请求的 success、error、finally 是否统一校验请求代次，当前材料没有证明完全覆盖。若要强化，应为每个结果槽引入 generation，所有写入和清理都验证请求归属。

主题三：任务恢复 ​

第一层： 离开页面后怎么恢复？

答：普通页面保存用户和主体对应的 taskId、输入、开始时间和阶段快照，五分钟内返回时带着原任务 ID 重新连接。

第二层： 为什么还需要 requestId？

答：恢复同一个服务端任务也会产生新的前端连接，所以必须为这次连接创建新的执行身份。requestId 防止旧连接或旧展示队列回写当前界面。

第三层： 如果旧 Promise 已经完成，只是后续展示动画还没结束，abort 能阻止它吗？

答：不能保证。abort 主要作用于网络读取，已经完成的 Promise 链和展示队列仍可能继续执行，所以还需要在每个关键回调提交前检查当前执行身份。当前外部结果回填分支的失效边界需要通过测试进一步确认。

主题四：技术选型 ​

第一层： 为什么是 SSE？

答：一次用户输入对应一个服务端任务，任务期间主要由服务端向前端持续推送阶段和结果事件，SSE 的通信方向符合当前场景。

第二层： 为什么不用 WebSocket？

答：当前不需要连接上的高频双向通信，WebSocket 会引入更复杂的连接和消息协议管理。若未来变成实时双向协作，再重新评估。

第三层： 自己解析 SSE 的代价是什么？

答：需要正确处理字节跨块、字符跨块、事件跨块、空行分帧、多行 data、异常响应和无终态断流；成熟库可以降低协议维护成本，但仍要核对它与后端业务事件的契约。当前解析器面向项目业务 data，不能包装成完整的标准 SSE 客户端。
