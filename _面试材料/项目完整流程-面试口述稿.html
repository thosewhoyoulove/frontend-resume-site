项目完整流程：面试口述稿 ​

用途：回答“介绍一下这个项目”“从用户操作开始讲一下完整流程”。先讲清业务如何跑通，再围绕面试官关心的环节展开技术细节。

事实来源：当前简历、项目技术尽调材料，以及本次补充的拓客 Agent 对话流程。本文未重新读取业务源码或运行项目。口述中的“我们”表示项目实现；涉及“我负责、我设计”的部分，应按本人实际贡献替换。

一、销售 / 拓客 AI Agent：一次完整对话 ​

本节以拓客嵌入场景为例。输入参数、本地先展示用户消息、创建会话后的路由同步，以及宿主通知行为来自本次业务补充；公共流处理、事件归并和请求隔离与已有尽调材料对应。

流程主线 ​

用户输入文本、选择附件和模式 → 整理发送参数并本地展示用户消息 → 创建或复用会话 → 发起 POST 流式请求 → 解码并解析 SSE → 校验当前执行身份 → 归并事件并更新消息 → 展示内容、工具卡片或确认操作 → 本轮结束，并向宿主同步相关变化。

面试口述 ​

我拿拓客 Agent 的一次完整对话来介绍。用户输入问题、点击发送之后，前端主要处理三件事：准备用户输入、确定会话身份，以及把后端持续返回的事件转换成界面上的消息和操作。

首先是发送消息。

我们会把文本、附件、当前模式和 Skill 等参数整理好，交给公共的 agent-core 处理。这里会先在本地插入用户消息，让用户点击后立刻看到自己的内容，然后继续走后面的请求流程。

接下来要确定这条消息属于哪个会话。

如果用户已经在一个会话里，就复用当前会话 ID；如果是首次发送，就先创建会话，拿到 ID 后再发起这一轮流式请求。

拓客场景比较特殊的地方，是 Agent 通过 iframe 嵌入业务系统。 创建会话后，Agent 内部要更新会话路由，宿主也需要更新对应的地址。我们通过 postMessage 通知宿主同步 URL，宿主同步地址时保持 iframe 实例继续运行。如果这时重新加载 iframe，就会销毁当前页面和流连接，打断正在生成的内容。

会话准备好之后，产品侧的 client 负责把参数转换成后端接口需要的形式，公共层再处理流式数据。我们使用 fetch 发起 POST 请求，通过 ReadableStream 持续读取响应，因为发送消息需要提交请求体，也需要接入取消机制。

这里读取到的每个网络块，并不一定是一条完整消息。一个中文字符可能跨块，一个业务事件也可能被拆成几段。所以会先用 TextDecoder 做增量解码，再通过文本缓冲拼出完整的 SSE 事件，最后由产品适配层解释业务内容。

后端返回的内容除了文本，还有执行状态、标题、工具调用、等待确认等事件。前端把这些事件交给公共层归并：同一个业务事件的后续更新落到同一条展示记录上，普通输出持续更新内容，工具事件展示对应卡片，需要确认时展示操作入口并进入等待状态。

如果用户确认继续，前端会把确认操作交给对应的业务接口，再根据后续返回更新执行状态。这个环节的具体接口和参数应结合实际代码展开；在这里，关键是把“等待用户操作”和“正在接收输出”区分开。

这条链路里另一个关键问题，是旧请求不能影响新一轮会话。 我们用 AbortController 管理连接，同时给每轮执行分配序号。开始新执行、切换会话或卸载时，让旧执行失效并取消连接。后续回调提交内容前还会判断自己是否属于当前执行，旧请求的收尾也只能清理自己的状态。

这样处理，是因为取消网络连接无法撤销所有已经进入 JavaScript 回调队列的工作。连接取消和执行身份校验分别负责资源释放与状态提交。

最后，新会话、标题和生成状态等变化会通知宿主，宿主可以据此更新侧边栏等区域。按照当前业务描述，这些状态通知不作为聊天继续执行的前置条件，宿主没有及时响应时，对话主流程仍然继续。

这条流程的核心，是把协议处理、事件归并和会话生命周期集中在 agent-core，产品侧负责接口、业务参数、扩展交互及宿主通信。 Sales 和拓客可以复用同一套公共能力，同时保留各自的业务差异。

追问时把握的边界 ​

  • 本地先展示消息属于即时反馈；失败后的消息标记、撤回和重试策略需要确认，不能由此推导已经具备完整的乐观更新回滚机制。
  • 标题、工具调用、等待确认等事件的精确字段，应以产品协议为准。当前状态映射不能直接称为完整状态机，历史材料显示错误和完成均可能映射到 completed。
  • 事件归并按业务标识更新展示记录，没有版本拒收证据，不能保证任意乱序事件都正确。
  • 前端停止接收与后端停止任务是两个动作；是否真正终止后端执行取决于服务端协议。
  • iframe 地址同步和宿主通知的实际消息名、发送时点、来源校验及失败处理，后续可通过 host-bridge 源码补齐。

二、高级筛选与 AI 智能搭建：从一句话需求到企业检索 ​

筛选与智能搭建流程主线 ​

用户输入自然语言需求 → 创建生成任务并接收阶段事件 → 展示生成进度 → 检查 ready 和条件对象 → 用统一快照回填筛选器 → 配置未就绪则暂存条件 → 携同一份条件发起企业查询 → 展示卡片或表格 → 用户调整、保存条件组或分享 → 离页时保存有效任务，返回时按条件恢复。

筛选与智能搭建面试口述 ​

这个项目可以从“用户想找一批企业”来讲。以前用户要自己组合行业、地区等筛选条件，智能搭建则允许用户先用自然语言描述需求，系统生成条件后，继续复用原来的检索、编辑和保存能力。

前端最主要的工作，是让生成任务和已有筛选系统衔接起来，并保证界面展示的条件与实际查询的条件一致。

用户提交需求后，我们通过 POST SSE 接入服务端的生成任务。后端会逐步返回阶段进度和结果，前端解析事件并展示执行过程，同时保存后端给出的 taskId，供任务恢复使用。

这里不会看到一段总结文案就直接查询。容器需要检查任务是否 ready，以及是否有条件对象，再把结果交给统一的 applyFilterSnapshot 入口处理。这样可以区分“已经有文字输出”和“条件已经可以进入业务系统”。不过，对象存在仍然只是基础检查，不能代表所有字段和操作符都已经通过完整校验。

接下来是条件回填，这是项目里比较典型的时序问题。

筛选器需要先加载维度配置，才能把接口条件转换成可展示、可编辑的结构。如果 AI 结果先返回，配置还没有到，立即转换就可能失败，或者被后面到达的默认值覆盖。

我们在配置没就绪时先用 pendingValue 保存待回填条件，等配置到达后优先处理这份条件，再清除挂起值。 这样生成任务和配置加载不需要强制串行，也有明确的衔接位置。

条件回填时，一方面更新容器条件与筛选器，另一方面把本次条件快照直接传给企业查询入口。原因是页面状态更新和后续操作可能交错，如果查询时再去读取某个可变状态，就不一定还是用户这次确认的条件。显式传快照能让这次回填与这次查询使用同一份输入。

页面同时支持手动筛选和智能搭建，也支持卡片与表格两种结果视图。我们把两种模式的条件分别保存，两种视图的数据、分页和 loading 也分别维护，避免切换时互相覆盖。

切换结果视图时，会检查目标视图有没有已完成的结果，以及查询键是否与当前条件匹配。匹配就复用，否则重新取数。请求忙碌期间再次筛选，会保留最新的一份待查条件，等当前查询结束后再执行，避免用户最后一次操作直接丢失。

结果出来后，用户可以继续手工修改条件，也可以保存为条件组或生成分享口令。分享口令读取到的条件同样进入回填流程，后面的检索能力可以复用。

还有一个场景是用户生成到一半离开页面。普通页面会按用户和业务主体保存 taskId、输入、开始时间及阶段快照，用户在有效期内返回时，可以携同一个 taskId 重新连接，并跳过已经完成的阶段展示。嵌入场景则关闭这套任务缓存，按独立策略处理生命周期。

流连接本身也会用请求序号和 AbortController 做隔离，避免正常启动新任务或离页后，旧回调继续更新界面。当前外部结果回填分支仍有需要验证的失效边界，不能把这个机制概括成所有竞态都已解决。

这条流程的价值，是让自然语言生成的结果进入已有的确定性检索链路：条件可见、可编辑、可查询，也可以保存和分享。 前端的难点集中在条件归属、配置时序和长任务生命周期。

筛选与智能搭建的能力边界 ​

  • Redux 提供配置、权限等上下文；条件、结果、分页和 loading 有一部分保存在组件本地，不能说全部由 Redux 管理。
  • 视图复用以查询键匹配为依据，没有完整 TTL 请求缓存或全局 in-flight 去重保证。
  • 忙碌期间保存的是最新一份待查条件，并不会把每次点击都加入 FIFO 队列。
  • 任务有效期从开始时间计算为五分钟；保存快照不会不断延长有效期。
  • 恢复属于任务级续接，没有消息游标级断点续传，也没有任意断网自动重连保证。
  • 外部回填时旧回调、结果请求乱序等问题在尽调材料中属于待验证或待强化项。

三、营销触达 SDK：从业务页点击呼叫到多页面状态更新 ​

SDK 流程主线 ​

宿主页面初始化 SDK → 选择 SharedWorker 或单页兼容通道 → 建立通信并取得初始化状态 → 用户发起呼叫 → 统一接口进入 BLL 及呼叫逻辑 → 呼叫状态写入模型 → Bridge 聚合本地变化 → 经 iframe 和端口同步到共享核心 → 广播到已连接页面 → 远端静默更新模型并通知 UI → 通话结束或页面退出时处理对应资源。

说明：以下呼叫执行与状态同步是相互配合的两条链路。共享核心处理业务消息和共享状态，不能据此认定 sip.js、音频媒体或实际通话运行在 SharedWorker 内。

SDK 面试口述 ​

我拿业务系统里的一次呼叫来介绍这个 SDK。用户在页面上看到的是点击呼叫、查看接通状态和挂断，但前端内部还要处理呼叫逻辑复用、宿主适配，以及多个页面之间的状态同步。

SDK 主要做的是把业务操作、状态模型和通信机制分开，让业务页面通过统一入口使用呼叫能力。

先看初始化。业务页面接入 SDK 后，会建立模型和通信通道。支持 SharedWorker 的环境通过隐藏 iframe 连接到共享 worker；iframe 还没加载好时，页面发出的消息会先暂存，加载完成后再继续发送。新页面接入后，也有获取当前共享状态的路径，避免只等待后续变化。

这里 iframe 负责宿主页面与资源域之间的桥接，SharedWorker 提供可共享的 JavaScript 上下文，MessagePort 负责具体消息传递。能不能共享，还取决于同源要求和浏览器的实际隔离策略。

如果环境没有 SharedWorker，SDK 会使用兼容 Bus，在当前页面内通过模拟桥和端口复用业务处理逻辑。业务入口仍可沿用，但这时只有单页能力，不能继续承诺跨 Tab 状态共享。

初始化完成后，用户点击呼叫。业务 UI 调用 SDK 暴露的接口，由 BLL 处理业务操作并与底层呼叫实现协作，Model 维护供界面使用的状态，Bridge 则负责状态变化如何进入通信链路。具体哪一种呼叫方式走哪些 sip.js 方法，需要结合对应调用链进一步说明。

呼叫过程中，拨号、接通、结束等变化会反映到模型。对于需要跨页面同步的本地修改，Bridge 会先聚合变化，再经 Bus、隐藏 iframe 和 MessagePort 发送到共享核心，由核心更新共享缓存并广播。

其他已连接页面收到广播后，会更新各自的本地模型，再通知业务 UI 刷新。这样多个页面可以反映同一份共享呼叫状态，页面本身不需要各写一套底层端口通信。

这里有一个重要细节：远端同步回来的状态，不能再次被当成本地修改发送出去。 否则 A 页更新传到 B 页，B 页又发送回来，就会形成重复广播甚至回环。当前 Bridge 接收广播时使用 noWatcherSet 静默更新，再单独通知视图，把远端回放与本地写入区分开。

通话结束后，呼叫逻辑更新对应状态，关联界面再按状态变化刷新。页面退出时，也有注销登记和挂断相关处理。不过，页面退出通知本身并不可靠，例如进程被强杀时就可能来不及执行，所以不能仅凭退出处理就说资源永远不会残留。

这个项目的核心，是让各业务系统复用相同的呼叫接口和状态传播路径，同时把宿主兼容问题集中在通信层处理。 它降低了重复接入成本，但多页面共享、单页降级和真实通话的生命周期要分别说明。

SDK 的能力边界 ​

  • BLL / Model / Bridge 是既有架构；未确认个人贡献前，采用“基于既有分层参与开发和维护”的表述。
  • 共享呼叫状态不能推导出媒体流共享，也不能推导出关闭当前 Tab 后通话自动迁移。
  • 兼容通道复用页内处理逻辑，没有 BroadcastChannel 跨页降级。
  • API 存在检测不能覆盖 worker 构造失败、CSP、iframe 超时等所有故障。
  • 来源精确校验、并发请求关联和统一资源释放仍有强化空间，不能说通信链路已具备完整可靠投递和安全保证。

四、千瓦能源管理平台：业务页面与图表展示（待补充实际页面） ​

当前材料只确认：参与平台从 0 到 1 建设，负责业务页面、ECharts 和公共组件，并主导技术栈迁移。没有具体页面、接口或实时数据机制证据。以下采用“用户打开一个数据页面”的通用骨架，需替换成实际做过的页面后再作为个人项目案例使用。

能源平台流程主线 ​

用户进入数据页面 → 确定查询条件 → 请求业务数据 → 整理图表和页面展示结构 → 渲染图表及其他业务区域 → 用户调整条件后重新查询 → 按实际页面生命周期处理图表实例。

面试口述骨架 ​

这个项目是物联网能源管理平台，我参与了从 0 到 1 的建设，主要负责业务页面、ECharts 可视化和公共组件。介绍完整流程时，我会选一个实际负责的数据页面，从用户进入页面开始讲。

用户进入页面后，首先要确定当前查询条件，再通过业务接口获取数据。数据返回之后，前端需要整理成页面和图表使用的结构，例如对应的维度、指标及系列数据，然后交给 ECharts 展示。

用户修改查询条件后，页面按新的条件重新取数，再更新相应展示。这里需要结合真实页面说明：哪些区域共用一次查询、哪些区域独立加载，以及空数据和接口失败时如何反馈。

图表部分不能只停留在“调用 ECharts”。 我会结合做过的图表说明，接口字段怎样映射到坐标轴和系列，公共组件封装了哪些重复配置，以及页面尺寸变化和离开页面时如何处理实例。这些需要以实际实现为准。

工程层面，我还主导了 Vue2 到 Vue3、Vuex 到 Pinia、vue-cli 到 Vite 的迁移。迁移中处理依赖兼容和构建配置，并结合模块拆分与按需引入，将构建耗时从约 60 秒降到 15 秒。这里的数字是简历中的历史自述，进一步追问时需要交代当时的环境和测量口径。

这个项目可以分两层讲：业务层说明数据怎样进入页面并形成可视化，工程层说明迁移如何落地、怎样确认原有业务仍可正常使用。 具体回归过程和发布方式，需要补充本人当时真实执行的步骤。

使用前需要补齐 ​

  • 一个真实页面的名称、使用者及核心操作。
  • 实际查询条件、接口数据结构，以及本人负责的具体图表。
  • 数据刷新方式：手动查询、定时轮询或其他机制，按实际情况填写。
  • 已实现的请求隔离、图表 resize / dispose、空态与错误处理。
  • 迁移中的一个具体兼容问题、解决过程及实际验证方式。

使用顺序 ​

先练各项目的“流程主线”，确保能够连贯说明输入、处理、状态与输出。再练口述正文，第一次回答可以只保留主要链路，关键问题等待追问展开。

需要解释具体方案、替代选项或失败时序时，配合 深度面试训练；需要查看已有源码证据和能力边界时，配合 技术尽调与强化路线。
